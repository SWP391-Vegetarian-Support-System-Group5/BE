# Recipe categories and legacy cleanup

## Changes

- New RecipeCategories table: Id, Name, Slug, Type, Description, ImageUrl, IsActive, CreatedAt.
- New RecipeCategoryMappings table: composite key (RecipeId, CategoryId).
- RecipeId references Recipes.PostId (the existing recipe primary key).
- Names use the existing PascalCase database conventions. JSON uses camelCase.
- Existing Categories/Posts.CategoryId remain post-level classifications; they are not recipe taxonomy.
- Tags/PostTags are removed from models, endpoints and payloads. No automatic conversion of sample tags into nutritional claims.
- MealPlans: removed BMR, TDEE, HealthGoal, TargetCaloriesPerDay from the model.
- MealPlanMeals: removed PlannedCalories from the model.
- VideoRecipeDrafts: removed Servings/CaloriesPerServing from model and DTOs.
- Recipes.Servings is retained; Recipes.CaloriesPerServing and UserProfiles.HealthGoal are removed.

## Deploy order

1. Back up VegetarianSupportSystemDB and stop old local API processes.
2. Build/test and deploy the new backend. With Database__RunStartupTasks=true (default), startup creates the two new tables before seed. This additive step does not drop legacy columns/tables.
3. Seed inserts 35 missing categories by (Type, Slug), leaving existing admin edits and inactive status intact. Dietary mappings for existing recipes are reconciled from classified ingredients; cuisine/lifestyle labels are not inferred from dish names.
4. Verify /api/recipe-categories returns data, then deploy the updated frontend.
5. Once every old backend instance has stopped, open MySQL Workbench on Aiven, select VegetarianSupportSystemDB and execute 20261014_RemoveLegacyFields.sql. It drops only the listed legacy columns and tables and does not create backup tables. It can be rerun. Column deletion is irreversible without a backup.

Do not run dotnet ef database update expecting these schema changes: this imported MySQL project currently excludes legacy EF migrations from compilation. RecipeCategorySchemaUpdate is the additive startup schema mechanism.
New data is seeded when you restart/deploy the API, not by executing the cleanup script alone.

## API

- GET /api/recipe-categories?type=CUISINE: active categories only.
- GET /api/recipe-categories?includeInactive=true: inactive included only for authenticated ADMIN.
- POST /api/recipe-categories and PUT /api/recipe-categories/{id}: ADMIN only.
- A category is hidden by setting isActive=false. Types cannot be changed after creation.
- Recipe create/update and video draft publish accept categoryIds (array, duplicates removed).
- GET /api/recipes/search?category=ID&categoryType=MEAL_TYPE&keyword=... supports the new taxonomy.
- GET /api/posts supports the same category/categoryType filters for recipe posts.
- Recipe responses expose categories with active metadata. No TagIds/Tags in payloads.
- Dietary labels are calculated by ingredient DietaryGroup. Incompatible manually submitted dietary labels are rejected. Empty/unverified recipes get no dietary labels. Pescatarian is not supported as a vegetarian diet.
- High Protein/Low Carb/Weight Management are editorial labels, not an automatic nutrition calculation or verification.

## Frontend

- /create-content: multi-select grouped categories; dietary labels are generated by the backend.
- /explore: real recipe data with category/type filters, replacing the old sample recipe section.
- /view-detail/{id}: displays active recipe categories.
- /admin/recipe-categories: create/edit/activate/deactivate categories.
- Browser-saved manual drafts now store selectedCategoryIds. Legacy tag selections are not mapped to the new taxonomy.
- Ingredient categories remain PLANT/DAIRY/EGG/HONEY with existing allergen references. A canonical Ingredients catalog is not introduced in this change.
